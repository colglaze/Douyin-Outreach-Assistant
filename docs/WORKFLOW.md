# WORKFLOW — 开发流程总纲（永久保留）

> 融合《项目计划书》的三级演进路线与 Harness 工程化体系（AGENTS.md / 文档治理 / 范围冻结 / 分阶段 DoD）。
> 本文档与 PRD 同级，永久保留；具体阶段执行细节见各 DEV 文档。

## 0. 一句话原则

**规划永远比写代码重要：任何一行代码产生之前，先有文档；任何一个阶段结束之前，先过 DoD。**

## 1. 文档系统（本项目的一切管理载体）

### 1.1 文档类型与命名

| 类型 | 命名格式 | 用途 | 写入时机 |
|------|----------|------|----------|
| PRD | `docs/PRD.md` | 产品总纲 | 立项时写一次，永久保留 |
| WORKFLOW | `docs/WORKFLOW.md` | 本流程 | 立项时写一次，永久保留 |
| AGENTS | `AGENTS.md`（根目录） | AI 行为规范与代码边界 | 立项时写，行为变化时改 |
| REQ | `docs/REQ-YYYYMMDD-XX-*.md` | 需求与范围冻结 | 新功能/大范围改造前**必写** |
| DEV | `docs/DEV-YYYYMMDD-XX-*.md` | 技术方案、模块拆解、阶段 DoD | 复杂模块实施前**必写** |
| BIZ | `docs/BIZ-YYYYMMDD-XX-*.md` | 业务流程或策略的确认与调整 | 业务决策变更时 |
| BUG | `docs/BUG-YYYYMMDD-XX-*.md` | 缺陷记录 | 发现 bug 立即记录 |
| PROG | `docs/PROG-YYYYMMDD.md` | 进度日志 | 每天一篇 |

### 1.2 关联规则（强制）

- PROG **必须引用**相关 REQ / BUG / DEV —— 进度可追溯。
- BUG **必须引用**来源 REQ —— 知道缺陷从哪个需求引入。
- BIZ **必须引用**对应 REQ —— 业务决策不悬空。
- REQ 验收标准被修改时，旧内容划线保留，注明修改日期与原因。

### 1.3 冲突优先级

```
AGENTS.md → 用户本次明确要求 → PRD → REQ → DEV → BIZ → PROG → 现有代码
```

代码与文档不一致时，不得静默猜测：按高优先级文档确认目标，说明差异并同步修正。

## 2. 完整开发流程（七步循环）

```
① 需求提出
    ↓ 写 REQ（范围 + 验收标准 + 明确不做什么）
② 方案设计
    ↓ 写 DEV（模块拆解 + 数据结构先行 + 阶段 DoD）；有业务歧义先写 BIZ
③ 数据模型
    ↓ 先改 src/types.ts 与存储结构，再写实现
④ 纵向切片实现
    ↓ 适配层 → 业务层 → UI 层，一次只切一个可验证闭环
⑤ 验证
    ↓ typecheck + build + 真实页面人工验证
⑥ 文档同步
    ↓ 写当天 PROG（状态/证据/遗留/下一任务）；bug 另写 BUG
⑦ 阶段门禁
    ↓ 对照 DEV 的 DoD 全部达标 → 进入下一阶段；否则留在本阶段
```

## 3. 阶段流水线（本项目实例）

| 阶段 | 内容 | 产出文档 | DoD（门禁） |
|------|------|----------|-------------|
| Phase 0 | 文档体系初始化 | AGENTS/PRD/WORKFLOW/REQ/DEV/PROG | 六类文档就位，范围冻结生效 |
| Phase 1 | 工程骨架 | — | typecheck 通过；esbuild 产出带油猴头的 user.js |
| Phase 2 | 核心链路（V0.1） | PROG | 达人页识别昵称/粉丝；悬浮按钮；打开私信并写入测试文字 |
| Phase 3 | V0.2 | PROG | IndexedDB 达人库 CRUD；模板变量替换；状态机流转 |
| Phase 4 | V0.3 | PROG | AI 润色（含降级）；防重复提醒；联系记录落库 |
| Phase 5 | 真实页面验证 | PROG + BUG（如有） | 抖音达人主页完整链路人工跑通，选择器校准 |
| Phase 6 | V1.0 插件化 | 新 REQ + 新 DEV | 另行立项：Chrome MV3 迁移，不在本 REQ 范围 |

**纪律：每个 Phase 达到 DoD 才能进入下一阶段，这个纪律不能破。**

## 4. 范围冻结纪律

- v1 做什么、不做什么，以 `REQ-20260902-01` 为准。
- AI 或人想"顺手加功能"时：对照 REQ——不在范围内的，新建 REQ 草稿排入后续版本，**本次不实现**。
- 变更产品范围/架构/阶段顺序：先更新对应文档，再编码。

## 5. 上下文管理（多对话协作规则）

- 每个对话最多实现 3~4 个需求，防止上下文压缩导致准确度丢失。
- 新对话开始时：先读 `AGENTS.md` + 最新 `PROG` + 当前 REQ/DEV，再动手。
- 按需加载：只把当前任务相关文件纳入上下文，其余通过文档索引知悉"存在但不加载"。
- 可交接性：换工具/换模型/换人，读一遍文档体系即可接手。

## 6. 缺陷与返工流程

```
发现 bug → 立即写 BUG 文档（关联来源 REQ，描述复现路径）
→ 修复 → 在 BUG 文档记录根因与修复方式 → 当天 PROG 引用该 BUG
```

抖音改版导致选择器失效是本项目最高频 bug 来源，修复时**只改 `douyin/selectors.ts`**，
并在 BUG 文档记录新旧选择器对照，沉淀为改版应对知识。

## 7. 节奏

- 每天结束写 PROG；每个 Phase 结束在 PROG 中做门禁小结（DoD 逐项打勾）。
- 每周回顾一次 REQ 范围冻结是否被侵蚀、文档是否与代码漂移。
